title: 把 KV Cache 的字节数先算出来

自回归生成第 t 个 token 时，这个位置的 query 要和前面 t 个 key 做注意力，对应的 value 再按权重相加。如果每生成一个 token 都把整段前缀重新送进网络，前面那些层的 key 和 value 会被反复计算。KV Cache 把已经算完的 key、value 留在显存里，新 token 只算自己的那一对，再追加进去。

预填充和解码因此不是同一种负载。提示词第一次进来，要按整段长度做前向，算力和显存带宽都高。之后每步只增加一个位置，计算量小，但要读出越来越长的缓存。服务如果把这两段合成一个延迟数字，排队和缓存命中会搅在一起。

缓存有多大，可以用这个式子估算：

```text
bytes ≈ 2 × layers × kv_heads × head_dim × seq × batch × bytes_per_elem
```

前面的 2 是 key 和 value 各一份。拿一组常见的量级：32 层，8 个 KV 头，头维度 128，fp16（2 字节），序列 8192，batch 为 1。先算 32×8×128 = 32768，再乘 8192 得 268435456，再乘 2×2 = 4，大约 1 GiB。这只是一份序列的缓存，不含权重，也不含激活。batch 提到 8，或者序列提到 32k，这块会线性涨。权重往往是固定的几 GB 到几十 GB，缓存则会随并发和上下文把卡先占满。

多查询注意力让一组 key/value 被多个 query 头共享，kv_heads 小于 query 头数，缓存按这个比例下降。分页缓存不把每个请求都按最大长度一次性占死，而是按块分配，短请求只拿它用到的块。相同的系统提示可以复用已经算好的前缀，避免每个请求都为同一段提示再付一次预填充。

调上下文窗口之前，先用上面的式子乘上你的并发。算出来的缓存如果已经接近单卡显存，再长的窗口也只是配置项，跑不起来。
