CPython 的 GIL 保护解释器自己的状态，包括对象的引用计数，以及“现在是哪个线程在执行字节码”。同一时刻只有一个线程在跑 Python 字节码。它不保护你在业务上定义的不变量。两个线程同时改同一份订单，该加的锁还是要加。

`i += 1` 在字节码里大致是取局部变量、取 1、做加法、写回局部变量。线程可以在这些指令之间让出 GIL。两个线程各做一次，可能都读到旧值，各写回旧值加一，最后只增加了 1。这和有没有 GIL 不矛盾：GIL 让单条字节码不被拆开，但没有把这四条字节码变成一个原子操作。

等待 I/O 时，CPython 会放开 GIL。线程堵在 `socket.recv` 上时，别的线程可以执行字节码。所以下载、读文件、等数据库的多线程能重叠等待时间。纯 Python 的数值循环不放开 GIL，开更多线程也不会用到更多核，时间主要花在抢这把锁。这种计算要并行，用多进程，每个进程有自己的解释器和自己的 GIL；或者把循环放进会在计算期间释放 GIL 的扩展里。

asyncio 在一个线程里切换协程，切换点是 `await`。它没有绕过 GIL，只是避免了线程切换。CPU 循环里没有 await，事件循环一样会被堵住。看一段 Python 并发代码，先找它在等待还是在算。等待可以放进线程或协程；计算放进进程；共享的可变数据单独加锁，不要假设 GIL 会替你锁住“余额不能为负”这种规则。
